Pipeline Facet Sync Scheduling

Notes for how integration facets are scheduled, how dependencies are included, and how per-integration or per-link cadence overrides are configured.

What Changed

The pipeline no longer has to enqueue every facet for an integration link on every scheduler tick. Scheduled runs now resolve a facet plan first, using each facet's configured interval, dependency list, previous sync_context.last_success_at, and any JSON overrides stored on the integration or integration link.

Manual queueing through the development dashboard can target a specific integration link and a specific set of facets. When dependency inclusion is enabled, the planner adds the required upstream facets automatically.

Important Files

File Purpose
packages/shared/src/pipeline/sync-plan.ts Shared planner that decides which facets should run.
packages/shared/src/types/integration.ts Defines FacetSyncConfig and the optional sync field.
packages/shared/src/config/integrations/*/index.ts Provider-level facet definitions and default sync policy.

Provider Defaults

Provider defaults live beside the integration config. Add sync to an item in supportedFacets. 

{
  facet: ProviderFacet.M365Identities,
  scopeLevel: 'link',
  db: { table: 'm365Identities', shape: {} },
  sync: {
    intervalMs: 60 * 60 * 1000,
    dependencies: [ProviderFacet.M365CAPolicies, ProviderFacet.M365Groups],
  },
}

If a facet does not define sync.intervalMs, the planner uses FULL_SYNC_INTERVAL_MS, currently 24 hours.

Override Precedence

The planner merges configuration in this order:

  1. Provider default from supportedFacets[].sync.
  2. Integration-level JSON from integrations.config.pipeline.
  3. Link/customer-level JSON from integration_links.meta.pipeline.

Later values override earlier values. This lets the platform define sane defaults while a specific customer link can run more or less often.

Integration-Level Override

Use integrations.config when all links for a provider should share the same cadence. 

{
  "pipeline": {
    "facets": {
      "m365_identities": {
        "intervalMs": 3600000,
        "dependencies": ["m365_ca_policies", "m365_groups"]
      },
      "m365_teams_config": {
        "intervalMs": 86400000
      }
    }
  }
}

Per-Customer / Per-Link Override

Use integration_links.meta when one customer or one link needs different timing. This is the preferred place for customer-specific exceptions. 

{
  "pipeline": {
    "facets": {
      "m365_identities": {
        "intervalMs": 900000
      },
      "m365_teams_config": {
        "intervalMs": 172800000
      }
    }
  }
}

Disabling A Facet

A facet can be disabled at the integration or link level. Disabled facets are skipped by scheduled runs and are filtered out of manual plans. 

{
  "pipeline": {
    "facets": {
      "m365_teams_config": {
        "enabled": false
      }
    }
  }
}

Dependency Behavior

Dependencies are declared by the facet that needs upstream data. For example, m365_identities depends on m365_ca_policies and m365_groups so MFA enrichment has the policy and group data it needs.

During scheduled runs, if a facet is due, its dependencies are added to the same run. During manual runs from the development dashboard, dependencies are added when the Include dependencies option is enabled.

Manual Development Queueing

The development dashboard is available at /setup/pipeline. It lets a developer:

  • Select an integration provider.
  • Select an active integration link.
  • Select one or more facets.
  • Choose whether dependencies should be included.
  • Force a run regardless of the configured interval.

The TRPC mutation accepts the same inputs:

trpc.pipeline.replay.mutate({
  linkId,
  mode: 'full',
  facets: ['m365_identities'],
  includeDependencies: true,
  force: true
});

Operational Notes

  • The scheduler still respects link-wide active-run protection. A pending or running sync run for the same link can prevent another scheduled run from being queued.
  • Facet completion is tracked in sync_context. The scheduler uses last_success_at to decide whether a scheduled facet is due.
  • Current sync mode is still effectively full sync. Cursor/incremental support is scaffolded but not active.
  • After changing shared package code used by workers, rebuild the relevant packages and restart the running worker process.
